# 출시 기획 에이전트 설계

- 작성: 2026-11-23 · 브랜치 `HSJ-agents` (main `b1eaa83`에서 분기)
- 참고: https://github.com/maclovedany/Herbal-Cosmetics-Planner (에이전트 구조만 참고, 코드 형식은 우리 사이트를 따름)

## 1. 왜 만드나

지금 사이트는 계절을 고르면 추천 후보 3개를 보여 주는 데서 끝나요. AI는 우측 상단 채팅 도우미 하나뿐이고, 후보·점수·라인 구성은 화면 코드(`src/app.js`, `src/config/rules.js`)가 계산해요.

이번에는 기획자가 고른 후보 하나로 **기획안**과 **광고·마케팅 시나리오 제안서**까지 만들어 주는 에이전트 묶음을 붙여요. 결과는 버전으로 저장하고, 마이 기획실에서 AI 챗봇으로 고쳐 새 버전을 만들어요. 이 사이트(에이전트)는 한방 뷰티 신규 브랜드 기획자에게 외부 판매할 제품이에요.

## 2. 목표 · 하지 않을 것 · 실패로 보는 것

**목표**
- 후보 하나 → 기획안 + 광고 시나리오 3개(시나리오마다 대표 이미지 1장)를 한 번에 만든다.
- 모든 결과는 검증 에이전트를 통과해야 저장된다(돌려보내면 한 번 고쳐 쓴다).
- 결과를 버전으로 저장하고, 마이 기획실에서 챗봇 → 미리보기 → 적용으로 새 버전을 만든다.

**하지 않을 것 (이번 범위 밖)**
- 트렌드 분석 에이전트(수집·축적), 목표원가·MOQ 계산 에이전트.
- 진행 단계 실시간 표시. 대기 화면만 보여 준다.
- 상세페이지 제작.

**실패로 보는 것 (돌아가도 실패)**
- 의약품식 효능 표현("치료", "염증 완화", "재생", "혈액순환 개선" 등)이 검증을 통과해 저장된다.
- 점수·가격·라인 구성 숫자를 AI가 새로 만들거나 바꾼다. 숫자는 코드 값만 쓴다.
- 남의 기획안을 읽거나 고칠 수 있다.
- API 키가 브라우저로 나간다.

## 3. 제약

- 화면은 지금처럼 Vite + 순수 JavaScript. 프레임워크를 바꾸지 않는다.
- 배포는 Vercel 서버 함수(`api/*.js`). 개발 서버에서도 같은 코드가 돌도록 `vite.config.js` 미들웨어에 연결한다(지금 `/api/chat` 방식과 같음).
- 글 생성은 Gemini(`GEMINI_API_KEY`), 이미지 생성은 OpenAI(`OPENAI_API_KEY`).
- 로그인은 이미 있는 Supabase Auth(카카오·이메일). 기획안 만들기·저장·수정은 로그인한 사람만.
- 화면 문구와 코드 주석은 지금 코드처럼 한국어 존댓말.

## 4. 고려한 방법

| 방법 | 내용 | 장단점 | 결정 |
|---|---|---|---|
| 1. 지금 사이트에 구조만 옮기기 | Vite+JS 유지, `server/agents/`·총괄·API 추가 | 기존 화면·채팅·Supabase가 그대로 산다. 팀원이 아는 코드 위에 쌓는다 | **채택** (사용자 선택) |
| 2. Next.js+TypeScript로 새로 | 참고 저장소와 같은 형식 | 형식은 같아지지만 화면을 모두 다시 만들어야 한다 | 제외 |

수정 방식은 **A. 미리보기 후 적용**(사용자 선택). 요청 즉시 새 버전을 만드는 방식(B)은 원치 않는 수정이 버전으로 남아 제외했다.

## 5. 에이전트와 단계

참고 저장소처럼 에이전트마다 **코드가 하는 확인**과 **AI가 하는 일**을 나눈다. 총괄이 차례로 부른다.

| 순서 | 에이전트 | 종류 | 하는 일 |
|---|---|---|---|
| 1 | 후보 생성 | 코드 | 요청의 `계절 + 원료 + 목적`으로 후보를 서버에서 다시 계산한다(점수·라인 구성·가격). 브라우저가 보낸 계산값은 쓰지 않는다 |
| 2 | 후보 생성 | AI | 원료 자료(쓸 수 있는 말, 산지, 경쟁 메모, 트렌드)로 근거 메모를 정리한다 |
| 3 | 작성 | AI | 기획안 작성 |
| 4 | 검증 | 코드 | 규칙 대조 (아래 6절) |
| 5 | 검증 | AI | 표현·근거 검토. 문제가 있으면 3번으로 **한 번** 돌려보낸다. 고친 뒤에도 남은 의견은 기획안에 "검토 의견"으로 함께 저장한다 |
| 6 | 디자인·광고 | AI | 시나리오 3개 작성 + 시나리오별 이미지 지시문 |
| 7 | 디자인·광고 | 코드 | 시나리오 문구도 4번 규칙으로 대조. 걸리면 그 문구를 빼고 의견에 남긴다 |
| 8 | 총괄 | 코드 | 버전 v1 저장 (이미지 칸은 비워 둔다) |
| 9 | 디자인·광고 | OpenAI 이미지 | 이미지 3장을 따로 요청해 만들고 저장소에 올려 v1에 채운다 (8절). 실패한 장은 빈칸으로 남는다 |

AI 응답은 모두 정해진 JSON 형식(Gemini `responseSchema`)으로 받고, 코드가 형식을 다시 확인한다.

## 6. 검증 에이전트 규칙 (코드)

- **광고 금지어**: 기획안·시나리오 모든 글에서 금지어 목록을 찾는다. 목록은 `src/config/rules.js`에 둔다(예: 치료, 완치, 염증, 재생, 혈액순환, 여드름 치료, 아토피, 처방). 걸리면 고칠 점으로 돌려준다.
- **숫자 일치**: 기획안의 제품·용량·정가는 1단계 후보 값과 같아야 한다. AI에게는 숫자를 쓰게 하지 않고, 저장할 때 코드가 후보 값을 붙인다.
- **가격 범위**: 후보 정가의 ml당 가격이 `PRICE_RANGE` 안인지 확인한다(밖이면 의견).
- **후보 밖 원료**: 글에 다른 원료 이름(원료 DB의 `herb`)이 나오면 고칠 점으로 돌려준다.
- **라인 구성 일치**: 기획안의 제품 목록이 `LINE_RULE`의 1차 구성과 같아야 한다.
- **기능성**: 미백(톤) 라인이면 "기능성 보고 필요"가 주의사항에 들어 있어야 한다.

AI 검토 항목: 의약품 오인 표현, 원료 자료에 없는 효능·수치 단정, 계절·목적과 맞지 않는 설명. 의견은 최대 5개, 문체 취향은 지적하지 않는다.

## 7. 결과물 형식

**기획안** `plan`: 콘셉트명, 콘셉트(2~3문장), 타깃, 핵심 문구 3개, 제품별 역할(제품 목록은 코드 값), 근거 메모, 주의사항, 검토 의견.

**광고·마케팅 시나리오 제안서** `scenarios[3]`: 제목, 콘셉트, 타깃, 채널(예: 인스타 릴스, 올리브영 상세, 매장 POP), 장면 구성 3~4컷(컷마다 장면 설명 + 카피), 대표 이미지 1장(`image_path`), 이미지 지시문.

## 8. 이미지 생성

- OpenAI 이미지 편집 API(`POST /v1/images/edits`)에 **그 라인의 용기 샘플 PNG**를 참고 이미지(`image[]`)로 넣고 지시문으로 광고 장면을 만든다. 샘플 위치: `public/IMAGE/LOGO/cheonghyang-logo-02/application-examples/` (toner·serum·cream·lotion-pump·mist).
- 모델은 환경변수 `OPENAI_IMAGE_MODEL`로 바꿀 수 있게 하고, 기본값은 구현할 때 문서에서 확인해 `server/llm/openai.js` 한 곳에만 적는다. [확인필요: 기본 모델 ID, 편집 API의 gpt-image 모델 지원]
- 이미지는 글 생성과 **따로** 만든다. 기획안(v1)을 먼저 저장한 뒤 화면이 `POST /api/plan-image`를 시나리오마다 1번씩, 3번 동시에 부른다. 요청 하나가 짧아져 시간 제한에 덜 걸리고, 이미지가 실패해도 기획안은 남는다. 실패한 장은 문안만 보이고 [다시 만들기] 버튼을 둔다.
- 참고 이미지 파일은 서버 함수가 읽을 수 있어야 한다. Vercel에서는 `vercel.json`의 `includeFiles`로 함수에 포함한다.
- **로고 없이 용기만** 쓴다. 샘플의 '청향' 로고·글자를 지운 무지 용기로 그리라고 지시문에 넣는다(브랜드명은 샘플용 이름이고 외부 고객에게 나가기 때문). 글자가 남을 수 있어 검증 대상은 아니고 [다시 만들기]로 대응한다.
- **색**: 원료별 패키지 색(`herb_designs`의 main·cap·liquid)과 그 계절의 **최신 트렌드 컬러 팔레트**를 지시문에 함께 넣는다.
- 트렌드 컬러 팔레트는 지금 데이터에 없다. 새 표 `color_trends`(계절, 색 hex 목록, 이름, 출처, 기준일)를 만들고, 디자인·광고 에이전트는 그 계절의 최신 1행을 쓴다. 행이 없으면 원료 색만 쓰고 결과에 "트렌드 팔레트 자료 없음"을 남긴다. 처음 넣을 팔레트는 출처를 확인해 따로 조사한다 [확인필요]. 나중에 트렌드 분석 에이전트가 이 표를 채운다.

## 9. 저장 (Supabase)

`supabase/schema.sql`에 추가:

- `plans`: id, user_id(기본값 `auth.uid()`), season, herb, purpose, title, created_at, updated_at
- `plan_versions`: id, plan_id, version_no, content(jsonb: plan + scenarios + candidate 값), source(`generate` / `edit`), edit_request(수정 요청 글), created_at. `(plan_id, version_no)` 유일.
- RLS: 두 테이블 모두 본인 행만 읽기·쓰기. 지금 `recommendation_history` 정책과 같은 방식.
- 저장소 버킷 `plan-images`(비공개): 경로 `{user_id}/{plan_id}/{version_no}-{n}.png`, 본인 폴더만 읽기·쓰기. 화면은 서명 URL로 보여 준다.
- 서버 API는 브라우저가 보낸 로그인 토큰(`Authorization: Bearer`)으로 Supabase 클라이언트를 만들어 쓴다. 그래서 RLS가 그대로 적용된다. 서비스 키는 쓰지 않는다.
- 새 버전 번호는 "최신 번호 + 1"로 쓰고, 동시에 두 번 저장해 유일 제약에 걸리면 409로 알린다.
- `color_trends`: 8절. 모두 읽기, 쓰기는 관리자(SQL)만.

## 9-1. 사용 제한 (요금제)

결제 연동은 없다. 이용권은 관리자가 SQL로 넣는다. 횟수 숫자는 `server/limits.js` 한 곳에 두어 요금제를 다시 계산하면 그 값만 바꾼다.

| 구분 | 새 기획안 | 기획안 1건당 수정(적용) |
|---|---|---|
| 무료 체험 (모든 로그인 사용자) | 평생 1건 | 5회 |
| 건당 이용권 | 이용권 1장당 1건 | 5회 |
| 월 구독 | 달마다 20건 (기존 5건에서 변경) | 5회 |

- 표 `entitlements`(user_id, kind: `single`/`monthly`, 남은 건수 또는 기간 시작·끝, created_at). 본인 것만 읽기, 쓰기는 관리자만.
- 사용량은 `plans`(생성 건수)와 `plan_versions`(source=`edit` 수)에서 센다. 따로 세는 표를 두지 않는다.
- 횟수를 넘으면 `/api/plan`·`/apply`가 402와 "요금제 안내" 문구를 돌려준다. 미리보기(`/preview`)와 이미지 [다시 만들기]는 횟수에 넣지 않되, 이미지 다시 만들기는 기획안 1건당 6회로 막아 비용 폭주를 막는다.
- 요금제 화면 문구는 "월 구독 (20건 …)"으로 바꾼다. 가격(₩29,000, 초과 건당 ₩4,900)은 그대로 두고 나중에 다시 계산한다 [확인필요].

## 10. API

| API | 하는 일 |
|---|---|
| `POST /api/plan` | `{season, herb, purpose}` → 1~7단계 → v1 저장(이미지 없이) → `{plan_id, version}` |
| `POST /api/plan-image` | `{plan_id, version_no, scenario_index}` → 8단계 이미지 1장 생성·업로드 → 그 버전의 `image_path` 채우기 |
| `POST /api/plan-edit/preview` | `{plan_id, base_version_no, messages}` → 챗봇 답 + 바꿀 내용 미리보기 `{reply, proposal?}`. 저장하지 않는다 |
| `POST /api/plan-edit/apply` | `{plan_id, base_version_no, proposal}` → 검증(4·5·7단계) → 필요하면 이미지 다시 생성 → 새 버전 저장. `base_version_no`가 최신이 아니면 409 |

로그인하지 않았으면 401, 남의 기획안이면 404.

- `/api/plan`은 글 생성 4~5회라 오래 걸린다. `maxDuration`을 300초로 두고, Gemini 한 번 호출 제한을 60초로 줄인다. [확인필요: 팀 Vercel 요금제의 최대 시간. 60초 제한이면 단계별 요청으로 나눠야 한다]
- 진행 단계는 화면에 보여 주지 않으므로 스트리밍하지 않고 한 번에 응답한다.

**검토 때 정한 세부 규칙**
- 숫자 검사: 코드는 원·ml·% 숫자가 후보 값과 다를 때만 거른다. 원료 자료에 있는 통계(예: 경북 48.1%)는 인용을 허용한다. 나머지는 AI 검토에 맡긴다.
- `/apply`에서 검증에 걸리면 몰래 고쳐 저장하지 않는다. 422와 고칠 점을 돌려주고, 챗봇이 이유를 보여 준 뒤 고친 미리보기를 다시 제안한다. 미리보기로 본 내용만 저장된다.
- 1차 구성의 `extra`(클렌저)는 제품 목록에 "준비 중"(용량·정가 없음)으로 넣고, 가격 검사와 이미지에서 뺀다.
- `src/config/rules.js`의 `import.meta.env.BASE_URL`은 화면 전용 파일로 옮겨, 서버에서도 rules.js를 불러올 수 있게 한다.

## 11. 화면

- **출시 기획실 상세 창**: [기획안 만들기] 버튼. 로그인 전이면 로그인 창을 연다. 누르면 대기 화면("기획안을 만들고 있어요. 1~3분 걸려요")을 보여 주고, 끝나면 마이 기획실의 그 기획안으로 이동한다.
- **마이 기획실**: 내 기획안 목록(계절·원료·최신 버전·수정일) → 기획안 보기(버전 선택, 기획안 + 시나리오 3개와 이미지) → 오른쪽 챗봇.
- **챗봇(수정용)**: 지금 `src/chat/chat.js`를 마이 기획실 안으로 옮긴다. 챗봇은 보고 있는 버전을 바탕으로 답하고, 수정이 필요하면 미리보기 카드("무엇을 → 어떻게")와 [적용] 버튼을 보여 준다. 이미지는 사용자가 이미지 변경을 요청했을 때만 다시 만들고, 나머지는 이전 버전 이미지를 그대로 쓴다.
- 헤더 우측의 AI Chat 버튼과 `/api/chat`의 독립 채팅은 없앤다.

## 12. 파일 구성

```
src/core/candidates.js     후보·점수 계산 (app.js에서 옮김. 화면·서버 공용, 순수 함수)
src/config/rules.js        광고 금지어 목록 추가
server/llm/gemini.js       기존 chatWithGemini + generateJson(JSON 응답)
server/llm/openai.js       이미지 편집 호출 (모델 ID는 여기에만)
server/agents/prompt.js    프롬프트 공용 설명 블록
server/agents/research.js  후보 생성 (코드 + AI)
server/agents/writer.js    작성
server/agents/verifier.js  검증 (코드 규칙 + AI 검토)
server/agents/designer.js  디자인·광고 (시나리오 + 이미지 지시문)
server/agents/editor.js    수정 요청 → 미리보기
server/orchestrator.js     총괄: 순서, 재작성 1회, 저장
server/store.js            Supabase(사용자 토큰) 읽기·쓰기, 이미지 업로드
server/limits.js           요금제 횟수 값과 확인
api/plan.js, api/plan-image.js, api/plan-edit/preview.js, api/plan-edit/apply.js
src/plan/                  대기 화면, 마이 기획실, 수정 챗봇
tests/                     검증 규칙, 에이전트 순서·재작성, 후보 계산 (가짜 AI 응답, vitest)
```

## 13. 만들 때 정할 것 (구현자 몫)

- 프롬프트 문장, 시나리오 채널 예시, 대기 화면 문구.
- 마이 기획실의 세부 배치와 스타일(지금 `styles.css` 톤 유지).
- 금지어 목록의 세부 단어(6절 예시에서 시작).
