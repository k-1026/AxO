## 1. 왜 바꿨나

| 문제 | 확인한 사실 |
|---|---|
| 트렌드 에이전트가 자료를 쌓지 않음 | 매시간 작업이 `idea/trend/beauty_trends.json` 하나를 계속 덮어썼다. 그 안에는 출처 22곳의 확인 상태와 업계 기사 8건뿐이었다. |
| 지시문 형식의 결과 파일이 없음 | 지시문의 `idea/trend/trend.json`(약재 검색 흐름)과 `트렌드스냅샷_YYYY-MM-DD.md`는 한 번도 만들어지지 않았다. 네이버 API 키가 없어 `datalab_collect.js`가 실행되지 않았다. |
| '📈 뜨는 원료' 기준이 늘 비어 있음 | 위 파일이 없어서 항상 '확인 필요'였다. |
| 늘 같은 추천 | 기준 버튼 조합이 같으면 결과가 항상 같았다. |
| GitHub 미리보기의 한계 | htmlpreview는 정적 파일만 보여 줘서 실시간 수집 서버를 돌릴 수 없다. |
| 화면 JS 하드코딩 | 원료·계절·디자인·가격·문구·트렌드 근거가 HTML 안에 박혀 있어서, 에이전트가 새 정보를 넣을 수 없었다. |

## 2. 기획자 지시문 (요약 · 순서대로)

1. 트렌드 서브에이전트가 매주 1회가 아니라 계속 자료를 수집·저장하고, 그 자료로 기획 포인트를 추천해야 한다.
2. 출시순위 근거나 기초라인 후보를 추천할 때, 기존 규칙 안에서 결과의 자유도를 더 줘야 한다.
3. htmlpreview가 아니라 자체 사이트로 만든다.
4. 덮어쓰지 말고 DB에 쌓아야 한다.
5. 현행 JS 하드코딩을 없애고, 에이전트가 모은 정보를 JSON·DB에 계속 쌓는다.
6. 지금까지 만든 HTML과 작업 과정을 `beautyagent`에 올린다.

다음 단계로 받은 지시 (아직 진행 중)
- 기준 선택 에이전트: 사용자가 기준 버튼을 고르는 기능을 지우고, 기준을 고르는 에이전트를 따로 둔다.
- 조사 에이전트: 기획자에게 선택권을 준다.
- 목표원가 계산 에이전트: OEM 견적·MOQ·리드타임, 채널별 수수료·할인 구조, 출시일 역산 결정 시한을 다룬다.
- 디자인 에이전트: 제품 컨셉에 맞춰 제품 이미지, 제품 사용 이미지, 모델 이미지, 제품 영상을 만든다.
- 피드백 에이전트: 사람이 결정하는 단계를 넣는다.
  - 1인 기획자 시점에서 후보 라인을 다시 추천받는 루프
  - 회의 피드백을 보완해 상세화면이 다시 나오는 루프
- 오케스트레이터 (가장 마지막): 조사 → 설명 → 문서화를 서브에이전트로 나눈다.

## 3. 만든 구조

```
브라우저 (beautyagent/site/public/index.html)
   │  시작할 때 GET /api/knowledge      ← 원료·계절·디자인·가격·문구 (DB 최신 버전)
   │  GET /api/beauty-trends            ← 업계 기사 해석 (DB에 쌓인 최신 버전)
   │  SSE /api/trend/stream             ← 새 기사 · 집계 · 1초 상태
   ▼
서버 (beautyagent/site/server.js, Node 기본 모듈만)
   ├─ 수집기: Google 뉴스 RSS 4초마다 1건 (키 없음)
   │         네이버 뉴스 8초 · 데이터랩 15분 (키가 있을 때만)
   ├─ 집계: 약재별 기사 언급(최근 7일 ÷ 그 전 21일 주 평균), 피부 고민 낱말 수
   └─ DB (idea/trend/live/trend.db, node:sqlite) — 쌓기만 함
```

### DB 표 (지난 줄을 고치거나 지우지 않음)

| 표 | 쌓는 것 |
|---|---|
| `articles`, `article_herbs` | 처음 본 기사, 기사에 붙은 약재 태그 |
| `fetches` | 요청마다 성공·실패 |
| `herb_stats`, `purpose_stats` | 10분마다 약재별·피부 고민별 집계 |
| `datalab_runs` | 데이터랩 판정 결과 (키가 있을 때) |
| `beauty_snapshots` | `beauty_trends.json`의 모든 버전. git 기록에서 지난 버전 22개를 되살렸고, 이후 바뀔 때마다 추가 |
| `knowledge` | 화면 지식 데이터 23종. 바뀔 때마다 새 버전 추가 |
| `agent_runs`, `decisions` | 에이전트 실행 결과, 기획자 결정 (피드백 루프용으로 준비) |

- 텍스트로도 남겨요.
  - `idea/trend/live/news.jsonl`: 기사를 한 줄씩 쌓아요 (커밋 대상).
  - `idea/trend/트렌드스냅샷_YYYY-MM-DD.md`: 날짜별로 하나씩 만들고 매시간 덧붙여요.
- 커밋하지 않는 파일: `trend.db`(바이너리, 실행 중 계속 바뀜), `state.json`(현재 집계 캐시), `fetch_log.jsonl`(요청 기록, 하루 2만 줄 이상). DB는 `news.jsonl`, 시드 JSON, git 기록에서 다시 만들 수 있어요.

### 하드코딩 제거 (지식 DB)

- 화면 JS의 데이터 선언 22개를 지웠다. 그 자리는 `let 이름;`으로 남기고, 시작할 때 `/api/knowledge`에서 값을 채운다.
- 지운 데이터: SEASONS, HERBS, DESIGN, FINISH, PURPOSE_LABEL, PRICE_RANGE, ITEM, LINE_RULE, ROLE, COMBO_WHY, TALK, PERSONAS, LIGHT, COMBO_KW, PAIN_KW, SAMPLE·PRODUCT_BOX, SEASON_TREND_NOTES, BEAUTY_TRENDS, TREND_SOURCES, TREND_TIERS, 신뢰 출처 도메인.
- 서버 하드코딩도 옮겼다: 원료 목록, 일반 검색어, 피부 고민 낱말, 기사 점수 구간.
- 처음 내용은 [beautyagent/site/data/seed/](site/data/seed/)의 JSON 23개다.
  - `tools/extract_seed.js`가 HTML에서 그대로 꺼냈다.
  - 셀러 한마디는 함수였는데 `{herb}` `{season}` 자리표시 문장 틀로 바꿨다.
- 새 정보를 쌓는 방법
  - 서버가 켜져 있을 때: `POST /api/knowledge` → 화면에 바로 반영돼요.
  - 서버가 꺼져 있을 때: `node beautyagent/site/kb.js put <kind> <file.json> --actor 이름 --note 메모`
  - 팀이 시드 JSON을 고칠 때: 1분 안에 새 버전으로 쌓여요. 에이전트가 쌓은 버전을 시드가 되돌리지는 않아요.

## 4. 화면에서 바뀐 것

- **실시간 뷰티 트렌드 말풍선**
  - 초록 점과 "마지막 요청 N초 전 · 누적 기사 N건"이 1초마다 갱신된다.
  - 기획 포인트를 최대 4개 보여 준다: 뜨는 원료, 떠오르는 피부 고민, 검색 흐름(데이터랩), 조용한 빈자리.
  - 기사 제목은 근거 링크로만 보여 준다. 기획 문구에는 의약품식 표현을 옮기지 않는다.
  - '방금 들어온 기사' 목록을 볼 수 있다.
- **'📈 뜨는 원료' 기준**은 두 가지로 판단한다.
  - 기사 언급 흐름 (실시간)
  - 데이터랩 검색 흐름. 키가 없으면 '확인 필요' 범위로 남는다.
  - 점수 구간은 **가정**이다 (`knowledge.news_rule`).
- **추천 폭 · 🎲 다른 추천 보기**
  - 이번 단계에서 넣었다.
  - 다음 지시에 따라 '기준 선택 에이전트'로 바꿀 예정이다.

## 5. 확인한 것 (브라우저 · 2026-11-17)

- 키 없이 Google 뉴스 수집이 작동한다. 첫 1분에 기사 58건, 이후 누적 177건을 모았다.
- 서버를 다시 켜도 DB의 기사·버전이 남는다.
  - 시험으로 검색어 1개를 추가해 `trend_queries` 버전 2를 만들었다.
  - 서버를 다시 켠 뒤에도 그대로였다.
- 하드코딩을 지운 화면도 지식 DB만으로 예전과 같이 나온다. 원료 12종, 위 3개 후보, 상세 화면이 모두 정상이다.
- 이미지 30장 중 깨진 것 0장, 콘솔 오류 0건.
- `beautyagent/site`로 옮긴 뒤에도 같은 데이터(IMAGE/, idea/trend/)로 작동한다. 서버가 저장소 맨 위 폴더를 스스로 찾는다.

## 7. 넣으면 좋은 API

| 우선 | API | 쓰는 곳 |
|---|---|---|
| 1 | 네이버 데이터랩(검색어트렌드 · 쇼핑인사이트) + 검색 — 키 하나 | 트렌드 (국내 검색·쇼핑 흐름), 경쟁 제품 가격 |
| 1 | 공공데이터포털 (식약처 원료성분 · 기상청 · 에어코리아) | 조사, 계절 기후 표 갱신 |
| 2 | Gemini API (이미지·영상 생성, Google 검색 연결) | 디자인, 조사 |
| 2 | YouTube Data API | 트렌드 (영상 관심 신호) |
| 2 | KOSIS · 한국은행 ECOS · 관세청 | 시장 규모, 목표원가 가정 범위 |

- 구글 키 하나(Gemini + YouTube)로도 시작할 수 있다. 다만 국내 검색량(데이터랩)과 쇼핑 클릭 흐름은 얻을 수 없다.
- Google 트렌드는 공개 API가 없다.
- OEM 견적·MOQ·채널 수수료는 API가 없어서 공개 자료와 '가정' 값(보수·기준·낙관)으로 다룬다.
